The problem this solves

A rule in CLAUDE.md is read once, when the session starts. It then sits at the top of the context while the conversation grows beneath it. Nothing checks whether I obey it.

So the rule works early and fades later. The fix is not a better rule. The fix is to move the rule closer to the moment I write.

When each mechanism fires

The two mechanisms trigger at different moments in a session. Read them left to right: the reminder reduces the distance between the rule and my answer.

Session start The rules load Once per session. The distance to my answer grows all session long.
Every message you send The reminder is injected Once per prompt, immediately before I answer.

Amber marks advisory mechanisms. They remind Claude Code to write clearly.

The two mechanisms

1  The rules themselves

~/.claude/CLAUDE.md · line 44
Advisory

A section named Writing: Simplified Technical English holds the rules, three worked examples, and a self-check list. It applies to every project on this machine, in every git worktree, whatever way Claude Code was installed. The file lives in your home directory, so the install method never matters.

One adjustment separates it from the published standard: it asks for ASD-STE100 principles, not the restricted vocabulary. Terms such as idempotency, webhook, coroutine and rate limiter stay.

2  The per-message reminder

hooks.UserPromptSubmit · ~/.claude/settings.json
Advisory

This hook runs every time you send a message. It prints one JSON object, and Claude Code injects the text into my context directly ahead of my answer. You type nothing.

It costs one printf and about forty tokens per message. It does not eliminate drift, but it removes the distance that causes drift. 

{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "Apply the STE100 writing rules from the
      session instructions. Before returning the answer, check for
      short sentences, active voice, one idea per sentence, and
      unnecessary words."
  }
}

What the rules ask for

ASD-STE100 documentation states its guidance as paired examples, under the headings Not approved and Approved. These three pairs are the ones written into the file.

Not approved Approved
The application will perform an evaluation of the incoming request prior to the execution of the synchronization process. The application checks the request before it starts the synchronization.
In the event that synchronization is unsuccessful, the operation will be retried. If synchronization fails, retry the operation.
This issue may potentially occur due to the fact that the connection has already been terminated. This issue can occur because the connection is already closed.

The rules behind those pairs: short sentences under 20 to 25 words, one main idea per sentence, active voice, simple words outside the technical terms, no idioms, and the same word for the same concept every time.

Where this still fails

Prose cannot be enforced by this kit. My sentences go straight to the terminal, and no tool call exists to inspect them before you read them. Every honest limit below follows from that fact.

Failure mode Why it happens
Long sessions The rules sit far above the work. The per-message hook shortens that distance but does not remove the effect.
Quoting and relaying Error output, log lines and subagent reports arrive in their own voice, and I carry it.
Matching a house style A formal PR template or a file's existing voice pulls against the rules.
Uncertainty When I am unsure, I hedge, and hedging produces the vague wording the rules forbid.
Mid-turn work The reminder fires once per message, not once per tool call, so a long turn gets it only at the start.
On the drift threshold. A percentage of the context window is a weak trigger, because drift tracks absolute distance rather than a share of the window. On a 1M window, 60% means roughly 600,000 tokens between the rule and the sentence. A trigger nearer 30–40% fits better, and any compaction should count regardless of the percentage. This is reasoning from the mechanism, not a measurement of my output.

Operating it

Run /hooks to see, edit or remove the reminder hook. It lives in ~/.claude/settings.json, so it is yours alone. Nothing was added to the repository, and your teammates are unaffected.

Two manual controls remain, and they are the strongest ones you have. Say “STE” and I will rewrite the last answer. Say “long session” and I will re-run the check list before the next one.
